# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Math Adventure" — a single-player, local-only (no backend) math practice game for the Massachusetts curriculum frameworks, grades 5 through 11 (the high-school years following the MA model course sequence: 9 = Algebra I, 10 = Geometry, 11 = Algebra II). Each grade has its own adventure map of themed worlds, each world holding several levels, with XP/streak/badge gamification layered on top. Grade 7 (strands 7.RP, 7.NS, 7.EE, 7.G, 7.SP) is the original hand-authored content; the other grades are generator-driven.

## Commands

```bash
npm run dev      # start Vite dev server (http://localhost:5173)
npm run build    # tsc -b (project-references build) + vite build — the real type check
npm run lint     # oxlint
npm test         # vitest run (unit tests for the pure-function core)
npm run contract:update  # regenerate the content contract — ONLY when deliberately breaking saves
npm run preview  # preview a production build
```

**Important: use `npm run build` (or `./node_modules/.bin/tsc -b`) to type-check, not `tsc --noEmit`.** The root `tsconfig.json` has `"files": []` and only `references` to `tsconfig.app.json`/`tsconfig.node.json` — a bare `tsc --noEmit` run against it is a silent no-op and will not catch real errors (including `verbatimModuleSyntax` violations and `noUnusedLocals`/`noUnusedParameters` violations, both enabled in `tsconfig.app.json`). Only `tsc -b` resolves the project references and actually checks `src/`.

## Architecture

Screen-based state machine (no router) driven by a single Zustand store (`src/store/gameStore.ts`), persisted to `localStorage` under the key `math-adventure-save`.

**Data flow:** `src/types/game.ts` defines the core discriminated unions (`Question` variants by `type`, `VisualHint` variants by `kind`) that everything else builds on. `src/data/questions/*.ts` each export a flat `Question[]` for one strand; `src/data/questions/index.ts` concatenates them into `allQuestions` and exposes `getQuestionById`/`getQuestionsForLevel` (levels reference questions only by ID string, never by object, so content can be edited without touching structure). `src/data/worlds.ts` defines the 5 `World` objects (each with 4 `Level`s), and `src/data/badges.ts` defines badge unlock conditions evaluated against store state.

**Store (`src/store/gameStore.ts`):** holds both persisted fields (`PersistedState`: XP, badges, per-level progress/stars, current world) and runtime-only fields (`currentScreen`, the active `run` — current level's question index/streak/correct count). `persist`'s `partialize` only saves the `PersistedState` fields. The initial `currentScreen` is computed synchronously from `localStorage` in `readInitialScreen()` at store-creation time (not via `onRehydrateStorage`, which has a temporal-dead-zone footgun if it tries to call `useGameStore.setState` from inside its own initializer — don't reintroduce that pattern).

**Adding content** — the whole point of the layout in `src/data/`:
- **A new level**: append to a world's `levels` in `src/data/grades/gradeN.ts`. Append only; unlocking chains by position, so inserting one re-locks everything after it.
- **A new world**: append to that grade's array in the same file. Same reason.
- **A new generator**: add it to a module in `src/data/generators/`, register it in that module's exported array, and reference it from a level. `registry.test.ts` fails if a generator is never referenced, since an unwired one ships silently and no student ever sees it.
- **A new grade**: create `src/data/grades/gradeN.ts`, widen `GradeId` in `src/types/game.ts`, and append one entry to `GRADES` in `src/data/grades/index.ts`. Nothing else — the picker, map, unlocking and review all read the registry. It used to also need two lookup maps and a CSS colour rule in `GradeSelectScreen`, where a forgotten colour failed silently.

`src/data/worlds.ts` holds NO content, only lookups over the registry, so editing content never means touching the code that reads it.

**Grades:** `World.id` is unique across grades (`g7-geometry`, `g8-geometry`), `World.strand` drives theming/icons and is shared across grades, and `World.grade` is a `GradeId` (5 | 6 | 7 | 8 | 9 | 10 | 11). **Never look a world up by strand** — `getWorld(id)` takes the full id and `getWorldForLevel(levelId)` is the way to get from a level to its world. Grades are freely selectable from `GradeSelectScreen` (a 9th grader shouldn't clear grade 7 first), so anything that reasons about unlock order must be handed **one grade's** world list via `worldsForGrade(grade)`; passing the full `worlds` array makes each grade's first world look gated behind the previous grade. Grade 7 is the hand-authored bank; grades 5-6 and 8-11 (`src/data/grades/gradeN.ts`) are entirely generator-driven, built with the shared `generatedLevel()` helper in `src/data/generatedLevel.ts`. A level's `strand` is theming, not a content taxonomy — a level may legitimately draw on a generator from another strand (grade 5's Fraction Falls reuses `ns-fraction-add`), and the test only requires that a level stay on one strand unless it sets `crossTopic: true`.

**Unlock logic** (`src/lib/unlocks.ts`): `isLevelUnlocked`/`isWorldUnlocked`/`hasAllStarsInWorld` are pure functions of `(worlds, state)`, always derived at read time rather than stored — both `src/data/badges.ts` and the screens import from here so unlock rules stay in one place.

**Screens** (`src/screens/`) are switched on `currentScreen` in `App.tsx` inside a single `AnimatePresence`: `OnboardingScreen` → `WorldMapScreen` → `LevelIntroScreen` → `GameplayScreen` → `LevelCompleteScreen`. Navigation is store actions (`selectWorld`, `startLevel`, `goToWorldMap`, etc.), not props/routes.

**Gameplay loop:** `GameplayScreen` reads `store.run`, resolves the current `Question` via `getQuestionsForLevel`, and passes it to `QuestionCard`, which does an exhaustive switch on `question.type` to pick the answer component (`MultipleChoiceAnswer` / `NumericAnswer` / `DragDropOrderAnswer` / `DragDropMatchAnswer` / `GraphPlotAnswer` / `ExpressionAnswer` — the drag-drop ones are actually tap-to-order/tap-to-match, not real HTML5 drag, chosen for touch/trackpad robustness). Answer correctness is checked in `src/lib/scoring.ts` (`isAnswerCorrect`, `starsForAccuracy`).

**Algebraic answers** (`src/lib/expression.ts`): `expression` questions are graded by *equivalence*, not string match — both the student's answer and `correctExpression` are parsed and evaluated at several mixed-sign, non-integer sample points, so `2(x+3)`, `2x+6` and `6+2x` all pass. Parsing is hand-rolled recursive descent over a restricted grammar — **never `eval`**, which would run whatever a kid typed. Because equivalence alone can't tell "expanded" from "unexpanded", an expand/factor question must also set `rejectSameAs` to the prompt's own form; without it a kid can copy the prompt back and be marked correct. Note a bare word parses as a product of single-letter variables (`alert(1)` is `a*l*e*r*t*1`), which evaluates to `NaN` and so never matches.

**Graph answers**: `graph-plot` questions have two modes. `points` compares a set of lattice points order-insensitively. `line` compares the *infinite line* through the two placed points via a cross-product collinearity test, so any two distinct points on the target line are accepted and vertical lines (undefined slope) work — don't reimplement this as a slope comparison. XP/streak-multiplier math lives in `src/lib/xp.ts`. Submitting an answer calls `store.submitAnswer`; continuing after feedback calls `store.advanceAfterFeedback`, which either advances to the next question or (on the last question) computes the full `LevelRunResult`, updates XP/progress/badges, and transitions to `level-complete`.

**Map rendering** (`src/components/map/`): world node positions are fixed coordinates in `mapLayout.ts`, which exports **two** layouts — `MAP_LAYOUT` (a wide 900×320 zig-zag, tablet and up) and `MAP_LAYOUT_PORTRAIT` (a 380×820 vertical trail for phones). `useMapLayout()` picks between them off a `(max-width: 640px)` media query and re-picks on rotate/resize; `WorldMapScreen` calls it and passes `nodes` down to `LevelPath` (the dashed SVG trail) and `WorldNode` (per-world SVG icon + progress ring + lock state), and into `getNodePosition(worldId, nodes)` for `Avatar` (tweens between world coordinates via Framer Motion). Don't reintroduce direct `MAP_LAYOUT` imports in those components — that silently pins them to the wide layout, which on a 375px screen collapses the whole map into a ~130px strip with clipped labels. All map/world art is inline SVG or CSS — no image assets. Note: a `motion.g` that animates `y`/`rotate` via Framer Motion will silently override any static `transform` attribute on that same element — bake positional offsets into the animated values instead (see `Avatar.tsx`'s bob animation, which had this bug once).

**Question generation** (`src/data/generators/`): each module exports `QuestionGenerator`s — `build(rng, difficulty)` returns a question with its computed answer, plausible distractors, and a **templated explanation that substitutes the actual numbers**, so it still walks through *this* problem. `src/lib/rng.ts` is a seeded PRNG (mulberry32), so a generated question's id (`gen:{generatorId}:{difficulty}:{seed}`) fully reproduces it — `parseGeneratedId` round-trips. A `Level` may list `generated` slots alongside its authored `questionIds`; `resolveLevelQuestions(level, attemptSeedFor(levelId, attempt))` concatenates authored-then-generated, and because the seed includes the attempt number, **replaying a level rerolls the generated questions** while the authored bank stays put. `startLevel` resolves this once and stores concrete `Question[]` in `run.questions` (runtime-only, never persisted) — don't reintroduce a per-render id lookup, since generated questions exist only for that attempt.

`generators.test.ts` sweeps every generator × 3 difficulties × 120 seeds asserting each question accepts its own stated answer, has no duplicate or secretly-correct distractors, keeps plotted points on the lattice and in bounds, and has a number-bearing explanation. It has already caught an inequality whose four options collapsed to two when x was 0, and a degenerate `4/4 = x/8` proportion — when adding a generator, add its degenerate case here rather than trusting a spot check.

**Cross-topic questions** (`src/data/generators/connections.ts`): generators prefixed `cx-` deliberately span two ideas a curriculum keeps in separate chapters, and each explanation names the link out loud — solving a system IS finding where two lines cross, factoring IS finding a parabola's x-intercepts, a unit rate IS a slope. `connectionsAdvanced.ts` reaches *above* the grade it sits in — slope as tan(θ), an average rate closing in on a derivative, area under a speed graph as distance — always answerable with the arithmetic the kid already has, with the new idea in the explanation. `connectionsClassic.ts` carries famous problems from other traditions (鸡兔同笼 chickens-and-rabbits, 盈亏 excess-and-deficit, work rates, meeting problems, Gauss's pairing, the Singapore bar model); each explanation gives BOTH the concrete classical method and the algebra it turns out to be. A level that deliberately spans strands sets **`crossTopic: true`** — `levelResolution.test.ts` checks that flag, not the title, so renaming a level cannot silently change what is enforced. crossTopic means "allowed to mix", not "must mix": a world's Challenge level is often single-strand.

**Primers** (`BaseQuestion.primer`): a short note rendered by `QuestionCard` *above* the prompt, before the kid answers, for questions using an idea or notation they may not have met — `f(x)`, "derivative", `log₍2₎`, `i² = −1`. The `explanation` teaches after the fact, which is right for reinforcing a known skill and useless for introducing a new one: without a primer a kid meeting a cross-topic question can only guess and then be told they were wrong. `generators.test.ts` holds the list of generators that must carry one, and asserts a primer never contains the answer verbatim (with a length guard, since a primer explaining `i` legitimately writes "−1").

**The content contract** (`src/data/contentContract.json` + `.test.ts`): a checked-in snapshot of every id a saved profile depends on — level ids, world ids, badge ids, generator ids, per-level pass thresholds, and world/level ORDER. `npm test` fails if any of those are removed, renamed, reordered, or made harder to pass, because each of those silently destroys real student progress with no error at the time. **Adding content always passes**; the contract exists to block destructive edits, not to freeze the curriculum. New worlds and levels must be APPENDED, since unlocking chains by position and inserting one mid-list re-locks everything after it. When a break is genuinely intended, `npm run contract:update` re-snapshots — which makes losing a student's progress a deliberate, reviewable act rather than an accident. Note tests are type-checked by `tsconfig.test.json` (which has node types) rather than `tsconfig.app.json`, so a test may use `node:fs` while app code still cannot reach `process`.

**Changing content later:** a save is keyed by **level id, world id, badge id and generator id** — never by question id. So editing a question's wording or numbers, changing a generator's internals, or adding/removing questions inside a level costs a student nothing. Renaming or deleting one of those four ids is the breaking move: `levelProgress` orphans (stars vanish, and the level reads as unplayed), a badge id orphan makes an earned badge re-earnable, and a `reviewSchedule` orphan used to **crash** the review session, since `getGenerator` throws — `planReviewSession` now takes `isKnown` and steps over ids the code no longer has. Two quieter traps: raising a level's `passThreshold` retroactively un-passes anyone whose stored `bestAccuracy` sits below the new bar (unlocking is derived at read time, not stored), and reordering worlds within a grade re-locks by index. Prefer adding a new id over renaming an old one.

**Content model conventions:** question IDs follow `{strandPrefix}-l{level}-q{n}` (`rp`, `ns`, `ee`, `g`, `sp`; levels 1–4; 9 questions each). `Level.questionIds` is just an array of these ID strings, generated in `worlds.ts` via `levelQuestionIds(prefix, level)`. When adding questions, append to the relevant strand file and reference the new IDs from `worlds.ts` — no schema changes needed. Every `Question` requires a non-generic `explanation` (shown after answering) — that's the pedagogical core of the app.

**Spaced repetition** (`src/lib/review.ts`): a Leitner box system scheduling question **types** (generators), never individual questions — every generator makes unlimited fresh variants, so "see this again in a week" means another question of that kind, which a kid cannot pass by recognising the numbers. Three kid-selectable ladders (`careful` 1/2/4/7…, `standard` 1/3/7/15…, `confident` 2/5/12/30…). A correct answer moves a type up a box; a miss drops it to box 0 and brings it back **tomorrow** — stepping back gently would leave something just failed sitting a month away. Scheduling is by local calendar DATE, not timestamp, so an evening and next-morning session count as two days. `advanceAfterFeedback` folds each finished run in via `applyRunToSchedule`, where a type counts as remembered only if *every* question of that type in the run was right. Review runs set `run.isReview`, use the pseudo-level id `__review__`, and score XP but no stars or level progress. `planReviewSession` keeps a session mostly grade-appropriate: above-grade types are capped at `MAX_ABOVE_GRADE_SHARE` (20%) so a grade 6 kid who once tried a grade 9 topic meets it occasionally rather than facing a review made mostly of untaught material. A generator's grade is the LOWEST grade whose levels use it (`src/data/generatorGrades.ts`), since many are drilled in one grade and revisited later. Below-grade types are never capped — that is revision. The ReviewCard shows the SESSION count, not the raw due count, because "7 due" beside a "Review 4 now" button reads as a bug.

**Sound** (`src/lib/sound.ts`): four effects (`correct`/`incorrect`/`levelUp`/`click`) synthesized with the Web Audio API — no audio assets are bundled. The `AudioContext` is created lazily on first playback because browsers refuse to start one before a user gesture. Every call takes `soundEnabled` and no-ops when false; `TopBar` owns the 🔊/🔇 toggle and reads `soundEnabled`/`toggleSound` straight from the store, so all three screens using `TopBar` get it without prop threading.

**Testing:** Vitest is configured inside `vite.config.ts` (node environment, `src/**/*.test.ts`). Tests cover the pure-function core — `scoring.ts`, `xp.ts`, `unlocks.ts`, `expression.ts` — since those decide whether a kid is told they're right or wrong. `.github/workflows/ci.yml` runs build (the real typecheck), lint, and tests on push and PR.

**Styling:** no CSS framework. `src/styles/theme.css` defines global CSS custom properties plus per-world theme classes (`.world-theme--{strandId}` setting `--world-primary`/`--world-secondary`/`--world-accent`), applied at the screen root so nested components can reference `var(--world-primary, <fallback>)`. Component styles are co-located (`Component.tsx` + `Component.css`).
